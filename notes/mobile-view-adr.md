# ADR: the raid-utility page gets a real mobile view

**Status:** **approved** 2026-08-03
**Date:** 2026-08-03
**Scope:** `docs/raid-utility.html` (generated), `docs/assets/raid-utility.css`,
`docs/assets/raid-utility.js`, `tools/utility_page.py`
**Supersedes:** nothing. Extends the one-screen layout contract recorded at
`docs/assets/raid-utility.css:45-68`.

---

## Context

The desktop page shipped and works. On phones the coverage grid renders at **zero
pixels** — not cramped, absent. Measured with Playwright across 11 viewports, a
raid loaded, 12 roster chips:

| case | viewport | chrome above `.ovbody` | `.mxwrap` height | tabs |
|---|---|---|---|---|
| iPhone SE portrait | 320x568 | 792 | **0** | 215 |
| iPhone 13 portrait | 390x844 | 738 | **0** | 215 |
| iPhone 13 portrait, 22px root | 390x844 | 946 | **0** | 254 |
| Pixel 7 portrait | 412x915 | 696 | **0** | 174 |
| **iPhone 13 landscape** | **844x390** | **420** | **0** | 95 |
| **Pixel 7 landscape** | **915x412** | **421** | **0** | 95 |
| Fold 5 inner | 673x841 | 488 | 195 | 139 |
| iPad mini portrait | 744x1133 | 489 | 505 | 139 |
| iPad mini landscape | 1133x744 | 398 | 207 | 95 |
| laptop | 1440x900 | 371 | 422 | 95 |
| desktop | 1920x1080 | 327 | 646 | 51 |

`document.scrollHeight === window.innerHeight` in **every** case. The document
never scrolls, so content past the fold is not merely small — it is unreachable.
At 320x568 roughly 220px of controls, including the add-a-walk-in field, cannot be
reached by any means.

### Mechanical cause

`raid-utility.css:69-74` makes `body:has(main.util.uwide)` a `height:100dvh;
overflow:hidden` flex column; `.util.uwide` is `flex:1;min-height:0`; `.mxwrap` is
`flex:1;min-height:0` (css:273). On desktop, chrome takes 371px and the grid gets
the rest. On a phone, chrome takes 738px of an 844px viewport, `flex:1` resolves to
zero, and `min-height:0` permits it. The contract is not being violated — it is
being honoured into a blank screen.

The sharper framing: **the stylesheet contains zero `min-width` media queries, and
the one-screen block at css:69 carries no media query at all.** It is a
viewport-locking layout shipped unconditionally to every device.

### Three findings that reframed the problem

1. **Landscape phone is a different bug and a worse one.** 844x390 and 915x412 are
   *above* the 720px breakpoint, so they receive the full desktop matrix
   (`table.mx{min-width:1040px}`, css:275) into a 792px box at 0px height. Rotating a
   phone crosses a width breakpoint that flips the rendering model into the worse of
   two. Any portrait-only fix ships a page that breaks on rotation.

2. **`100dvh` + `overflow:hidden` pins iOS to the small viewport permanently.**
   Safari's toolbar retracts only in response to document scroll. This document
   cannot scroll, so `dvh === svh` forever and the phone pays a ~110px toolbar tax it
   structurally cannot earn back. Document scrolling does not merely fix the zero
   height — on iOS it *recovers* ~110px the current model cannot access.

3. **Text scaling defeats any "reserve N pixels" fix.** At a 22px root (Android
   "Largest", iOS Dynamic Type XXL) chrome at 390x844 grows 738 → 946px. The
   one-screen model must die on phones rather than be tuned.

### The mobile transform already exists and has never been seen

`@media (max-width:720px)` (css:661-699) already turns `table.mx` into a per-class
card stack: `table{display:block}`, `tr.mxr` into a flex card, `td.mxx{display:none}`,
`td.mxv` prefixed by `content:attr(data-l)`. That is a genuinely different component,
not a shrunk grid. It has never been visible on a phone because the height contract
starved it. **The mobile view was already built; it was starved, not missing.**

---

## Decision drivers

- The owner's bar: the grid must have real height at 390x844 and 412x915 with a raid
  loaded.
- The owner's directive: mobile is a separate view, not a squeezed desktop.
- Desktop is shipped and liked. The bar for it is **zero pixels of change** at
  1440x900 and 1920x1080.
- `docs/raid-utility.html` is generated by `tools/utility_page.py`. Hand-edits are
  not an option.
- The page must survive with JS off — the noscript contract at
  `docs/raid-utility.html:14-31` promises server-rendered content degrading to a long
  scroll, not a blank screen.

---

## Decision

### D1 — One artifact, separate layout *mode*. Not a second HTML file.

One generated document, one URL, one stylesheet, one generator pass. Mobile-only
DOM is emitted by `utility_page.py`; mode selection is CSS; behavior is progressive
JS.

**Why not a second artifact.** Routing on GitHub Pages has four implementations and
all four are wrong. A JS UA sniff costs a full extra RTT on the connection least able
to afford it and `location.replace` removes the back-button escape. A `matchMedia`
width redirect is wrong the moment the device changes state — rotate an iPad, unfold a
Fold, drag a Stage Manager tile — and redirecting on resize discards the loaded raid,
roster edits, filter, open tab and scroll position mid-use. Server-side negotiation
does not exist on Pages, and a CDN that varied would cache one variant and serve it to
everyone. `<link rel="alternate" media>` is a crawler hint no browser navigates on.
All four fail silently and per-device, on a page a raid lead opens once, on a phone,
ten minutes before pull.

Three further arguments:

- **The URLs are already in Discord.** `raid-utility.js:589` documents the sharing
  convention in its own comment: `raid-utility.html?event=<id>` pasted "in the raid
  channel". Those links are pinned and permanent, and the people opening them are by
  definition on phones.
- **Payload runs against a split.** The document is 576KB raw / 70KB gzipped. A second
  artifact reduces nothing unless it omits rows, and omitting rows makes mobile *less
  capable* — the complaint inverted. The mode-switch CSS is ~3KB gzipped.
- **Drift is demonstrated, in this very file, inside one codepath.** Ten
  `href="#matrix"` links against zero `id="matrix"`. ~50 lines of `.scarcity` CSS
  (css:217-260) for a component the generator emits zero times. An unread `conf` at
  `utility_page.py:426`. A noscript comment still promising "the scarcity counts" that
  were deleted. Two codepaths would compound this, and `utility_page.py:517` already
  makes exactly this argument about roster data: "a second hand-maintained copy on a
  web page is a copy that is wrong."

**The honest concession:** a second artifact would be right if mobile needed different
*data*. It does not. The existing card mode renders a completely different object from
the same DOM. This is a re-presentation, not a different dataset.

### D2 — Three independent axes replace one conflated `max-width`.

The current stylesheet decides everything by width. That is why `(hover:none)` ended
up meaning "phone" and why rotation flips the grid's rendering model.

| axis | question | trigger |
|---|---|---|
| **Layout mode** | does the page own the viewport, or does the document scroll? | `@media (min-width:721px) and (min-height:760px)` |
| **Grid form** | matrix, or per-class cards? | `@container (max-width:1040px)` on `.mxwrap` |
| **Control sizing** | 44px targets? | `@media (pointer:coarse)` |
| **Which affordance fires** | hover card, or tap sheet? | `ev.pointerType`, per event |

The axes cross at different points on purpose. A 1024x600 netbook gets the *matrix*
(it fits) inside a *scrolling document* (no height to lock). That combination is
unreachable in a single-breakpoint model and is the right answer for that machine.

### D3 — Layout mode: `(min-width:721px) and (min-height:760px)`, height first.

The one-screen block (css:69-74) and the `flex:1;min-height:0` chain through
`.ovbody` / `.panel` / `.mxwrap` (css:105-112, 272-273) move **inside** that query.
Outside it — now the default — the document scrolls normally.

**Why both terms.** A phone fails a different term in each orientation. Portrait is
tall and narrow (390x844: fails width). Landscape is wide and short (844x390: passes
width, fails height). A height-only rule fails portrait; a width-only rule fails
landscape. This is not a compromise between two numbers — it is what the measurements
force.

**Why 721 and not 1000.** Both fix an identical set of broken devices. 1000
additionally drops iPad mini portrait (744x1133) out of one-screen mode, where it
measures a working 505px grid today. 721 costs zero working devices; 1000 costs that
one. Recorded limit of the approximation: a synthetic 768x800 passes 721/760 and
delivers only 243px of grid, below the 320px invariant. Every real candidate clears
it — iPad split-screen views are either under 721 wide or over 820 tall; laptops are
≥800 tall but ≥1280 wide. The invariant is enforced by assertion A11, not by the media
query; if a real device is found in that band, the height term rises. That is a number
change, not a design change.

`760` is derived as measured chrome at ≥721px width (327-400px) plus a 360px grid
floor. **It is provisional** — it was derived with a 12-signup raid before the chrome
collapse lands, and should be re-derived downward afterward rather than left as
folklore.

### D4 — Grid form: a container query at the table's own declared minimum.

```css
.mxwrap { container-type: inline-size; container-name: grid; }
@container grid (max-width: 1040px) { /* the current css:661-699 card block, verbatim */ }
@supports not (container-type: inline-size) {
  @media (max-width: 720px) { /* the same block, today's threshold */ }
}
```

1040 is not a guess — it is `table.mx{min-width:1040px}` (css:275). The rule becomes:
*the matrix renders as a matrix exactly while it fits, and becomes cards the instant it
does not.*

This fixes two things at once. It closes the ~721-1092px band where the matrix
horizontally overflows and the page ships the exact defect css:649-660 claims to have
fixed ("six of the ten columns lived off-screen behind an affordance the page never
offered"). And it makes **rotation form-invariant** — a phone's `.mxwrap` is ~792-810px
in both orientations, under 1040 either way, so rotating no longer changes the
rendering model. That is the single most valuable property in this ADR.

**Rejected: lowering `table.mx{min-width:1040px}` by demoting `.spn`** (the named spec,
css:424) to a marker at narrow widths. css:407-423 is an extended argument that a lit
*fraction* answers "how many specs" when the reader's question is "*which*", that 33 of
103 abilities are single-spec, and that 7 of the 19 classes with an interrupt are
spec-locked — so an Accursed Bloodmage brings no interrupt at all while its cell paints
solid. Demoting `.spn` re-introduces the exact failure that block was written to fix, at
the widths where the reader has least room to recover from being misled. A matrix that
lies is worse than a card stack that does not.

### D5 — The first screen is a gap-first answer block, with the class cards below it in the same scroll.

The primary phone task is **"is tonight's raid missing anything, and who can I ask?"**
Nobody raids from a phone. The phone reader is the raid lead on Discord an hour before
invites, or in the portal room with eight minutes to pull. That is a *tool-first*
question, not a class-first one.

The answer is **already computed** and currently rendered only as decoration on an
object the phone cannot see: `recount()` (js:103-152) builds `cover` = tool → how many
rostered classes can press it; `gaps()` (js:159-167) reduces it to the list nobody can
press. Today that surfaces as red `.gapcol` headers on an invisible grid, a clause in a
wrapping sentence, and `.tab.nocover` pills in a six-row strip.

So mobile gets `.cov`, a server-rendered coverage block, above the class cards:

1. `header.site` 54px, scrolls away (already `position:relative` — see D9).
2. **Sticky:** the 44px status line — raid title, staleness, headcount, gap count,
   collapsed filter icon.
3. **`.cov`, capped.** 0 gaps → one summary line. 1-2 gaps → individual named red rows,
   because each is actionable. **3+ gaps → a single red row naming them comma-separated**
   (the `.gapline` string `drawRaid()` already builds, js:341) plus the summary — when 4
   of 11 tools are uncovered the raid has a composition problem and the headline matters
   more than the breakdown.
4. **`tr.mxr` class cards immediately below**, roster-first.

**A ledger has no absence problem, and the file concedes the matrix does.** css:848-858
records that in a presence-painting grid "a tool nobody can press … renders as an empty
column" — invisible — which is why `.gapcol` had to be invented as a red wash. A gap in
`.cov` is a row that says NOBODY, in red, at the top of the screen. The matrix hides
gaps and needs a patch; `.cov` *is* the gap report.

**This does not demote the matrix.** An earlier draft put the class cards behind a "By
class" tap. The arithmetic says they fit together in one scroll, so the extra tap was
removed. The owner's literal bar — the grid has height on the first screen — is met
directly rather than relocated.

**Arithmetic at 390x844** (measured: usable width 366px, ledger rows 68px with a clamped
who-line, class cards 121px median, tabs 0px, status line 44px):

| gaps | `.cov` | consumed above cards | left for cards | first card fully visible (121px) | 3 card tops on screen |
|---|---|---|---|---|---|
| 0 | 72 | 170 | 674 | yes | yes — 0/121/242 |
| 2 | 208 | 306 | 538 | yes | yes |
| 4 (collapsed) | 179 | 277 | 567 | yes | yes |

At a 22px root, 2 gaps leaves 468px and three card tops at 0/155/310 — passes. At a 26px
root (162%), the first card is fully readable and the rest are one scroll away, which is
the correct outcome at that text size rather than a defect.

### D6 — The tab strip is hidden on mobile; `.cov` rows are the navigation.

14 tabs are ~1190px of strip against 366px of usable width — **4.3 of 14 tools visible**.
A horizontal scroller is acceptable for navigation and unacceptable for an answer, and
css:654-656 already litigated this exact failure for the matrix. With `.cov` above
carrying the gaps, each `.cov` row links to its panel and the strip is redundant.

**Mechanism: `display:none`, never removed from the DOM.** `gaps()` iterates `$$(".tab")`
and reads `t.firstChild.textContent` (js:159-167); `apply()` writes the badges
(js:761-782). `display:none` also removes the orphaned `role="tablist"` from the
accessibility tree, so there is no ARIA to reconcile — but `.cov` rows must then carry
proper `aria-controls` rather than being orphaned links.

> **Referee ruling, not agent consensus.** The two reviewers crossed on this item —
> each conceded to the other's position in the same round, so only one of them holds
> this on the record. I ruled for hiding because it is the later and better-informed
> position and it is what the responsiveness review's own round-2 concession argued for.
> Flagged here because it deserves the owner's eye. The alternative — a sticky 48px
> single-row scroller — is buildable, needs `display:contents` on `.ovtop` to escape its
> containing block, and makes the missing tablist ARIA mandatory rather than moot.

### D7 — The roster collapses to one line. Editing moves behind a tap, and the form is a full-screen route.

`.rhbar` measures 387px at 390px wide and **441px at 320px** — 46% and 78% of those
viewports — for the list of who signed up, when the pill above it already names the raid.
`raid-utility.js:348-353` argues the roster must always be visible because "the roster IS
the context for every number on the page". On desktop, at one band's cost, that holds. On
a phone it buys 37-78% of the screen when the reader's actual need is the count and the
gap verdict.

Collapsed: one 44px line carrying the Discord mark, title, `.rhage` staleness, headcount,
and derived gap count. `.rhstate`'s unmatched-signup warning stays visible whenever
non-empty — it is an error about data integrity, and errors do not hide.

**The editor splits in two, and this is not cosmetic.** The read-only roster list (`.pl`
chips, their 44px `.pdrop`, and `restore N removed`) may be a bottom sheet — no keyboard,
no problem. The **add-a-walk-in form must be a full-screen route** with the form at the
top of the panel. iOS Safari does not resize the layout viewport for the keyboard;
`visualViewport` only *reports* the occlusion. A bottom-anchored sheet is anchored to the
exact edge the ~330px keyboard takes, so it does not get out of the way — it gets covered.
The ~80-option `<datalist>` becomes a filtered list against the alias resolution that
already exists (`terms()`/`ALIAS`, js:657-674).

### D8 — Touch gets the detail sheet, decided per event rather than by media query.

`@media (hover:none){.abcard{display:none !important}}` (css:817) deletes the hover card
on every touch device at every width. That card is the only place the page shows spell
detail and `bearers()`'s "who in tonight's raid can press this / not on your Felsworn:
both are Tyrant" list (js:904-938). So the richest affordance on the page is unreachable
by finger — **including on a 1133px iPad that renders the full desktop matrix.**
`(hover:none)` is being used as a proxy for "small" and it is not one.

Final rule, three concerns and three different gates:

| concern | gate |
|---|---|
| sheet *presentation* (bottom-anchored, dismiss model) | `@media (hover:none)` |
| control *sizing* | `@media (pointer:coarse)` |
| **which affordance fires** | **`ev.pointerType`, per event** |

The third is the one that matters, and both media-query-only proposals left a bug
shipped. On a **touchscreen laptop** `(hover:none)` is false, so `bind()` (js:978-987)
keeps only `mouseenter`/`mouseleave` — and a finger fires `mouseenter` with no
`mouseleave`, so the card opens and never dismisses. `bind()` therefore keeps its mouse
listeners **unconditionally** (desktop byte-identical) and gains a `pointerdown` path
that opens the sheet when `ev.pointerType !== 'mouse'`. Capability detection at the
moment of use beats any media query here.

Sheet content is the full card — cooldown, cost, cast, chips, description, bearers — with
no second tap, but **reordered so `bearers()` comes before the description**. `one()`
(js:940-962) emits bearers last, so on a 70dvh sheet the answer to "so who DOES have it"
is the thing most likely below the fold. Implemented as `one(a, sheet)` with the falsy
default producing today's string byte-for-byte.

### D9 — Bugs found on the way, fixed in the same change.

Not redesign. Each is a defect against current behavior, and several become load-bearing
the moment mobile scrolls.

- **`--bandh` is read and never written.** `.mx thead .mxhead th{top:var(--bandh,29px)}`
  (css:280); nothing in the CSS, JS, or generator sets it. The band row measures 31px at
  default root and 38px at a 22px root, so the second sticky header already overlaps by
  2px, and by 9px under text zoom.
- **`.mxwrap` is a scroll container with `tabindex === null`.** A keyboard user cannot
  scroll the only scrolling box on the page. Safari does not make it focusable heuristically.
- **`body.rhlock{overflow:hidden}` (css:961) is an inert scroll lock that becomes a live
  iOS bug the moment mobile scrolls.** `overflow:hidden` on `body` does not prevent scroll
  in iOS Safari. **This must ship in the same commit as document scrolling** — scrolling is
  what makes it load-bearing.
- **Sticky will silently fail unless two ancestors change.** A sticky element does not
  stick if an ancestor has `overflow` other than visible on the same axis. `.util.uwide` is
  `overflow:hidden` (css:74) and `.panel:not([hidden])` is `overflow-y:auto` (css:111).
  Both become `visible` in scroll mode. No error, no warning, no obvious cause.
- **`header.site` is not sticky on this page.** `header.site.haspt{position:relative}`
  (site.css:445) overrides the `position:sticky` at site.css:72, and the page carries
  `class="site haspt"`. So `scroll-margin-top:74px` at css:182, 604 and 606 compensates for
  a sticky header that does not exist, and must be re-derived from the real sticky bar
  height via one shared custom property rather than a fourth hardcoded number.
- **Ten `href="#matrix"` against zero `id="matrix"`.** Shipped, dead.
- **`.rhmodal` uses `4vh`, not `4dvh`** (css:964) — on iOS `vh` is the *large* viewport.
- **`#panel-overview` has `padding-bottom:0`** (css:112). Correct in a clipped box; under
  document scrolling the last card lands flush against the viewport edge.
- **Character names break naive truncation.** The live roster contains
  `𝓥𝓾𝓵𝓽𝓱𝓻𝓪𝓼𝓾𝔃` — 10 glyphs, `String.length === 20`, astral-plane surrogate pairs. Any
  `.slice(0,n)` splits the pair and emits U+FFFD. Clamp with CSS ellipsis, never in JS.
  The hazard already exists in shipped `fillWho()` (js:689-709) and `bearers()`
  (js:904-938), not only in new code.
- **`conf` (utility_page.py:426-428) is computed and never read.** Surfaced narrowly as a
  `?` marker on a `.cov` count *only* when `cover > 0 && conf === 0` — the raid's entire
  coverage of that tool rests on abilities with no database record, i.e. "you might have
  this, or you might have nothing." That is gap-adjacent. Every other verified/unverified
  split is a caveat that already lives in the ability list as `.chip.unv`.

### D10 — Tap targets are fixed by name, not by sweep.

70 sub-44px controls on desktop, 78-80 on phones. The two that matter by volume are
`.pick` (the class icon in all 21 grid rows — the *primary* roster control) and `.pdrop`
(12 drop-a-no-show buttons).

**A blanket `min-height:44px` under `(pointer:coarse)` is rejected.** It would inflate
`.chip` (css:586), `.abwho i` (css:1047), `.pl` (css:874), `.mxlegend i` (css:450) and
`.rhwho i` (css:167) — which are *labels, not controls*. That eats the screen and, worse,
*implies* tappability that does not exist. A 44px non-target is a worse defect than a 20px
label. The spec carries an explicit allowlist and an explicit exempt list, and the harness
asserts the exempt list **stayed small** so a future sweep fails the test.

## Consequences

**Good**

- The grid has real height on the first screen at 390x844 and 412x915 — the owner's bar,
  met directly rather than relocated.
- Landscape phone is fixed, and rotation stops changing the rendering model at all.
- iOS recovers ~110px of viewport that the one-screen model structurally could not access.
- 320x568 stops amputating ~220px of controls.
- Touch devices get spell detail for the first time, including iPad, which is a live bug
  today at every width.
- ~50 lines of dead `.scarcity` CSS get revived rather than deleted; ten dead anchors,
  an unread `conf`, and a stale noscript comment get resolved.
- Text scaling has headroom: chrome drops from 738px to ~218px at 390x844, and still
  leaves 544px of content at a 22px root.

**Costs and risks**

- **Every rule moved into a media query is a rule that can silently stop applying on
  desktop, and there is no CSS test harness.** The before/after geometry assertion must run
  *before* the layout change lands, not after.
- The container query is ~93% baseline. The `@supports` fallback retains today's 720px
  behavior, which means two threshold values live in the file simultaneously and can drift.
  Both are asserted.
- `container-type: inline-size` on `.mxwrap` establishes containment; `.mxc` is
  `position:sticky;left:0` *inside* it (css:337). Sticky within the same scroller survives
  containment, but this is asserted rather than assumed.
- **`.cov` becomes a fifth surface for the same truth** (today: `.gapcol` headers, the
  `.gapline` sentence, `.tab.nocover` badges). If `apply()` is not the single writer for
  all of them they will disagree the first time someone touches js:761-782.
- **`apply()` multiplexes and must not reach `.cov`.** Search hits beat raid coverage and
  `.nocover` is suppressed unless `mode === "raid"` (js:766-778). If `.cov` inherited that,
  typing one character in the filter would silently convert the mobile home screen from a
  coverage report into a search-hit count **with every gap flag removed**. `.cov`'s coverage
  number and gap state are never multiplexed; search hits render as a second, differently
  styled number.
- `order:` changes visual order without changing DOM order, so roster-first cards read in
  source order to a screen reader (WCAG 2.4.3). This is the same cost `li.ab.notmine{order:2}`
  (css:1028-1030) already pays on this page — named here rather than inherited silently.
- **Headless Chromium reports `dvh === svh === lvh`.** Every iOS dynamic-toolbar bug, the
  `body.rhlock` scroll-lock failure, rubber-banding, and keyboard occlusion are invisible to
  Playwright. A manual iPhone pass is a real dependency, not a formality. The design
  deliberately *removes* the `dvh` mechanism rather than tuning it, so the two worst cases
  cannot fail by construction.

## Decisions the owner made — 2026-08-03

All four open decisions were resolved in favour of the reviewers' recommendations.

1. **Container-query threshold: 1040.** The table's own declared minimum. Eliminates the
   ~721-1092px horizontal-scroll band. Accepted cost: desktop browser windows narrower than
   ~1092px show the class-card form instead of a scrolling matrix.
2. **iPad mini landscape (1133x744) leaves one-screen mode** — accepted. A 207px window onto
   a 1444px table becomes a scrolling page with ~500px of cards. The only currently-working
   device the fix changes.
3. **The matrix's 2D form does not survive on a phone** — accepted. The class cards are the
   mobile grid form, directly below the answer block in the same scroll. Same 21 rows, same
   data, different shape.
4. **D6 confirmed as ruled** — tabs hidden on mobile, `.cov` rows are the navigation. The
   sticky 48px scroller is rejected. Recorded above as a referee ruling rather than agent
   consensus; the owner endorsed it explicitly.
5. **`conf`:** surfaced narrowly per the spec — a `?` marker only when
   `cover > 0 && conf === 0`. Not deleted.

## Alternatives rejected

| alternative | why rejected |
|---|---|
| Second HTML artifact / second generator codepath | All four routing implementations fail silently and per-device; Discord links are already pinned; payload argues against; drift demonstrated inside one codepath already |
| Raise the existing 900px breakpoint | The chrome itself is the problem — 6 rows of tabs and 12 always-visible roster chips are a desktop affordance. A breakpoint change does not shrink them |
| Keep `100dvh`, just shrink chrome to ~145px | Defeated by text scaling (738 → 946px at a 22px root) and forfeits the ~110px iOS toolbar recovery that only document scrolling unlocks |
| Container query for the *layout mode* | Impossible. `@container` size queries need `container-type: size`, which needs content-independent height — exactly the flex-collapse that produces 0px. It would query the collapsed height and confirm it |
| `(pointer:coarse)` for the layout mode | Input device has nothing to do with whether `flex:1` resolves to a usable number. An iPad Pro at 1366x1024 is a good one-screen experience and is coarse-pointer |
| JS-measured available height written to a custom property | Genuinely correct, and rejected: it reintroduces a layout-thrash loop that fires on every iOS toolbar transition, and it breaks the noscript path |
